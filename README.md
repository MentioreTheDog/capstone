# Прогноз удовлетворённости клиента для маркетплейса Olist

Предсказывает, что клиент поставит низкую оценку (1–2 звезды) после доставки заказа — используя только данные, известные **до** того, как отзыв оставлен. Решает конкретную бизнес-задачу маркетплейса Olist: заранее выявлять заказы из группы риска, чтобы поддержка могла вмешаться (компенсация, извинение) до публичного негатива.

---

## Датасет

- **Источник:** [Brazilian E-Commerce Public Dataset by Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce) на Kaggle — реальные анонимизированные коммерческие данные, не синтетика.
- **Размер:** 9 связанных таблиц, ~99 441 заказ; после фильтрации по доставленным и объединения с отзывами — **95 823 заказа**, 27 признаков.
- **Период / охват данных:** заказы с 2016-10-03 по 2018-08-29.
- **Ключевые признаки:**
  - `late_days` / `is_late` — опоздание относительно обещанной даты доставки (в календарных днях) — **главный признак модели**
  - `delivery_days`, `promised_days`, `seller_handling_days` — сроки доставки и сборки заказа
  - `n_items`, `n_sellers`, `total_price`, `total_freight` — состав и стоимость заказа
  - `product_category`, `product_weight_g`, `product_photos_qty` — характеристики товара
  - `customer_state`, `seller_state`, `same_state` — география
  - `payment_type`, `installments` — способ оплаты
  - **`review_score`** → `low_review` — целевая переменная: 1 = оценка 1–2 звезды, 0 = оценка 3–5

Признаки собраны SQL-запросом с JOIN и агрегацией по 9 таблицам (`feat_sql.py`), а не только средствами pandas — см. раздел «Методология».

## Исследовательские вопросы

1. Как распределена целевая переменная и какой порог бинаризации (1–2 vs 1–3 звезды) обоснован с точки зрения бизнеса?
2. Что происходит с пропущенными значениями и какого они происхождения?
3. Как соблюдение обещанного срока доставки связано с итоговой оценкой — и отличается ли это от влияния абсолютной длительности доставки?
4. Какие второстепенные факторы (категория товара, состав заказа, география, цена, способ оплаты) влияют на удовлетворённость?
5. Можно ли предсказать негативную оценку с качеством, полезным для бизнеса, учитывая сильный дисбаланс классов (12.8% негатива)?

## Методология

1. **База данных:** 9 CSV загружены в SQLite (`01_build_db.py`), добавлены индексы по ключам join'ов и `ANALYZE` для планировщика запросов.
2. **Сборка признаков:** один SQL-запрос с CTE, `JOIN` и оконными функциями (`ROW_NUMBER() OVER (PARTITION BY order_id ...)`) — выбор главного товара и основного платежа заказа, агрегация транзакций и оплат (`feat_sql.py`).
3. **EDA:** распределение оценок, обоснование порога бинаризации, разбор пропусков, связь сроков доставки, категории, географии и способа оплаты с оценкой — каждый график с текстовым выводом (`02_eda.ipynb`).
4. **Подготовка целевой переменной:** `review_score ≤ 2` → негатив (12.8% выборки); порог обоснован тем, что именно 1–2 звезды создают публичный репутационный риск, в отличие от нейтральной 3.
5. **Построение моделей:** Logistic Regression (база), Random Forest, HistGradientBoosting — со стратифицированным train/test split, `class_weight="balanced"`, подбором гиперпараметров через `RandomizedSearchCV` (`scoring="average_precision"`).
6. **Оценка качества:** PR-AUC как основная метрика (устойчива к дисбалансу 12.8/87.2), ROC-AUC вторично, порог классификации подобран по F1 на out-of-fold предсказаниях обучающей выборки (не на тесте).
7. **Интерпретация:** permutation importance по PR-AUC, проверка устойчивости модели на разбиении по времени, перевод метрик в операционную пользу (lift-анализ: сколько недовольных клиентов перехватывается при обработке top-N% заказов).

## Результаты

| Модель | ROC-AUC | PR-AUC | F1 @ 0.5 |
|---|---|---|---|
| Logistic Regression | 0.748 | 0.417 | 0.39 |
| Random Forest | 0.765 | 0.468 | 0.46 |
| HistGradientBoosting | 0.762 | 0.478 | 0.41 |
| **HistGradientBoosting (подобранный)** | **0.761** | **0.478** | — |

Модель **HistGradientBoosting** достигла **PR-AUC = 0.478** — почти в **4 раза выше** базового уровня случайного угадывания (0.128). На подобранном пороге (0.219): Precision 52%, Recall 42%.

- **Опоздание относительно обещанной даты — доминирующий фактор** (доля негатива растёт с 9–12% до 32–79% при срыве срока); абсолютная длительность доставки влияет заметно слабее — клиента раздражает не долгая доставка, а нарушение обещания.
- **`n_items` (число позиций в заказе) — второй по важности признак**, вклад втрое выше, чем у `delivery_days`: заказы из нескольких позиций/продавцов едут частями и рискованнее.
- **Бизнес-применение:** обработка top-5% заказов по риску перехватывает 29% будущих негативных отзывов при точности 75% — в 5.8 раза эффективнее случайного выбора. Рекомендуемый режим для поддержки — 5–10% заказов.

## Ограничения

- Датасет ограничен периодом 2016–2018 и одной страной (Бразилия); паттерны логистики могут не переноситься на другие рынки.
- Причины негатива, не связанные с логистикой (качество товара, несовпадение с ожиданиями, брак), в данных физически отсутствуют — модель не может их предсказать в принципе. Опоздавших заказов всего 6.7% выборки, что задаёт объективный потолок recall.
- При переносе на более поздний период (тест по времени вместо случайного) PR-AUC снижается — модель требует периодического переобучения в проде, а не одноразового деплоя.
- Текст отзывов сознательно не используется (вне рамок задачи и курса) — это оставляет неиспользованным потенциально сильный источник сигнала.
